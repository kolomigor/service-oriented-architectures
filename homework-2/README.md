# Marketplace: OpenAPI + CRUD

Вторая домашняя работа: API товаров, заказов и промокодов с PostgreSQL,
JWT и тремя ролями. Реализация на Go; приложение разделено на модули
внутри одного процесса. Это позволяет менять заказ, остатки и счётчик
промокода в одной транзакции PostgreSQL.

## Запуск

Нужен запущенный Docker с Compose. Все команды выполняются из `homework-2`.

```bash
cp .env.example .env
docker compose up --build -d --wait --wait-timeout 90
curl -i http://localhost:8080/health
```

Ожидается `200` и `{"status":"ok"}`. В Compose работают PostgreSQL и API;
Flyway применяет миграции, а bootstrap создаёт администратора и завершается.
Исходники генерируются во время Docker-сборки, локальный Go для запуска не нужен.

Для локального запуска предусмотрен администратор:
`admin@example.test`, пароль `LocalAdmin123!`. Эти значения и JWT-секрет
из `.env.example` предназначены для разработки. Значения можно заменить в `.env`;
bootstrap создаёт пользователя только при отсутствии email и не меняет пароль
у существующего администратора.

```bash
docker compose ps -a
docker compose logs -f app
docker compose down
```

Остановка сохраняет данные в Docker volume. Если порт занят, поменяйте
`HTTP_PORT` или `POSTGRES_PORT` в `.env`. По умолчанию API доступно на 8080,
PostgreSQL — на `127.0.0.1:5433`.

## Что реализовано

| Пункт | Реализация |
|---|---|
| 1 | Пять CRUD-операций товаров, пагинация и точные фильтры |
| 2 | Отдельные схемы создания, обновления и ответа; enum, nullable, required и форматы |
| 3 | Генерация DTO, серверного интерфейса и маршрутов из OpenAPI одной командой и при сборке |
| 4 | PostgreSQL, Flyway, индекс по status, автоматические даты и мягкое удаление |
| 5 | Единый JSON ошибок и весь каталог бизнес-кодов |
| 6 | Проверка запросов по OpenAPI до вызова бизнес-логики; details.fields |
| 7 | Транзакционные заказы, ограничения частоты, остатки, снимки цен, скидки и состояния |
| 8 | JSON-лог каждого запроса, UUID request_id, X-Request-Id, маскировка чувствительных полей |
| 9 | Регистрация, вход, access JWT и одноразовые refresh JWT с ротацией |
| 10 | USER, SELLER, ADMIN, проверка владельца товаров и заказов |

## Контракт и кодогенерация

Источник контракта — [api/openapi.yaml](api/openapi.yaml).
Он содержит запросы, ответы, ошибки и ограничения всех эндпоинтов.
Внешние тела запросов и ответов представлены сгенерированными DTO;
ручные транспортные модели не используются.

```bash
make generate
make build
make validate
make test
```

Для этих команд нужен Go 1.26+. Версия генератора закреплена в
`api/generator.mod`, его зависимости — в `api/generator.sum`.
Конфигурация — `api/codegen.yaml`. Результат — `internal/api/api.gen.go`;
этот файл исключён из Git и Docker-контекста и воспроизводится при сборке.

Сгенерированные маршруты вызывают обработчики в `internal/httpapi`.
Middleware проверяет тело, параметры, enum и ограничения через `kin-openapi`,
а затем обработчик вызывает модуль бизнес-логики в `internal/service`.
Проверки, зависящие от БД, выполняются внутри транзакции.

Денежные значения представлены точным `decimal.Decimal`, а в PostgreSQL —
`NUMERIC(12,2)`. В JSON передаются числа. Скидка округляется до двух знаков
после точки; процентная скидка дополнительно ограничена 70% суммы с округлением
этой границы вниз до копеек. Вычисления не используют двоичную арифметику
с плавающей точкой.

## Эндпоинты и роли

| Метод и путь | Доступ |
|---|---|
| GET /health | Без токена |
| POST /auth/register | Без токена; USER или SELLER |
| POST /auth/login | Без токена |
| POST /auth/refresh | По refresh token |
| GET /products, GET /products/{id} | Все три роли, любые товары |
| POST /products | SELLER и ADMIN |
| PUT /products/{id}, DELETE /products/{id} | SELLER для своих товаров; ADMIN для любых |
| POST /orders | USER и ADMIN |
| GET /orders/{id}, PUT /orders/{id}, POST /orders/{id}/cancel | USER для своих заказов; ADMIN для любых |
| POST /orders/{id}/status | ADMIN, последовательные переходы состояния |
| POST /promo-codes | SELLER и ADMIN |

Операции с товарами, заказами и промокодами требуют заголовок
`Authorization: Bearer <access_token>`.
Регистрация не позволяет получить ADMIN. Продавец создаёт товар с собственным
`seller_id`; назначить чужого владельца через тело запроса нельзя.
Администратор при создании товара записывается его владельцем.
При изменении остатка учитываются резервы отменяемых заказов: новый остаток
вместе с резервами должен помещаться в INTEGER, чтобы возврат товара был возможен.

`GET /products` принимает `page` (с 0), `size` (по умолчанию 20, максимум 100),
`status` и `category`. Фильтры сочетаются через AND; категория сравнивается
точно с учётом регистра. Без фильтра статуса видны и архивированные товары.
`totalElements` учитывает фильтры до пагинации. Порядок — новые товары сначала,
при одинаковой дате по ID. Страница за пределами списка возвращает пустой `items`.

`PUT /products/{id}` заменяет изменяемые характеристики. Пропущенное или `null`
описание очищает его. `DELETE` устанавливает `ARCHIVED`, запись остаётся в БД.
Повторное архивирование успешно и не меняет дату.

Access token действует 20 минут, refresh — 14 дней. В `.env` можно задать
access 15–30 минут и refresh 7–30 дней. JWT подписывается HS256;
проверяются подпись, issuer, срок, тип токена и пользователь в БД.
Refresh хранится в БД в виде SHA-256-хеша, используется один раз
и заменяется новым в транзакции. Пароли хешируются bcrypt.

## Заказы и транзакции

При создании проверки идут в порядке условия: лимит частоты, активный заказ,
существование и активность товаров, затем остатки. После этого резервируются
остатки, сохраняются цены, применяется промокод и записывается операция.
Любая ошибка откатывает всё, включая остатки и счётчик промокода.

Пользователь может иметь только один заказ в CREATED или PAYMENT_PENDING.
Это проверяется в логике и защищено частичным уникальным индексом в БД.
Операции пользователя сериализуются блокировкой его строки; товары блокируются
в порядке ID, а промокод — после товаров. Это предотвращает перепродажу
последней единицы и одновременное расходование последнего использования промокода.

Обновление доступно только в CREATED: возвращаются прежние остатки,
проверяются и резервируются новые позиции, пересчитываются сумма и скидка.
Уже включённые товары сохраняют цену из снимка заказа; новые позиции получают
текущую цену каталога. Повторяющиеся product_id в одном запросе отклоняются.

Если новая сумма ниже min_order_amount, промокод снимается и его использование
возвращается. Для оставшегося промокода повторно проверяются срок и активность;
его уже занятый этим заказом слот не считается исчерпанным для самого заказа.
Отмена из CREATED или PAYMENT_PENDING возвращает остатки и использование
промокода один раз. Повторная отмена запрещена.

```text
CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED
   │              │
   └── CANCELED ←─┘
```

Основную цепочку переводит администратор через `/orders/{id}/status`.
Отмена выполняется отдельным `/orders/{id}/cancel`.

В условии фраза о процентной скидке неоднозначна: «но не более 70% ...
в ином случае цена 100%». Принято буквальное толкование: значение процента
до 70 включительно применяется, свыше 70 скидка равна нулю. Для FIXED_AMOUNT
скидка ограничена полной суммой заказа.

`ORDER_RATE_LIMIT_MINUTES` задаёт N минут отдельно для CREATE_ORDER
и UPDATE_ORDER; по умолчанию N=1. Для обновления учитывается владелец заказа,
даже если действие выполняет администратор. Неуспешные операции в журнал
user_operations не записываются.

## Проверки

Юнит-тесты проверяют денежные расчёты, переходы состояний, JWT, ограничения
OpenAPI, сериализацию ответов и JSON-логирование без утечки паролей и токенов.

```bash
make test
go vet ./...
go test -race ./...
```

Для E2E нужен запущенный Compose и Python 3 без дополнительных библиотек.
Сценарий создаёт собственные данные с уникальными именами и оставляет их в БД.
Чтобы быстрее проверить лимиты, временно сократите N до 0,01 минуты:

```bash
ORDER_RATE_LIMIT_MINUTES=0.01 docker compose up --build -d --wait --wait-timeout 90
E2E_RATE_LIMIT_SECONDS=0.6 make e2e
docker compose up -d --wait --wait-timeout 90 app
```

Последняя команда возвращает настройки `.env`. Для другого адреса API
укажите `E2E_BASE_URL`. Если менялись учётные данные администратора,
передайте скрипту `ADMIN_EMAIL` и `ADMIN_PASSWORD`.

E2E проверяет CRUD, роли, контрактные ошибки, создание/изменение/отмену заказов,
снимок цены, промокоды, откаты транзакций и гонки за остатками/промокодом/refresh.

Посмотрите запросы в логах: `docker compose logs --no-color app`.
Для каждого есть UUID, метод, путь, HTTP-статус, время выполнения и user_id.
Пароли и токены в телах заменены на `***`.
